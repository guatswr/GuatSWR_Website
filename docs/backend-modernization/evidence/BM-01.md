## 实现与范围

- app 导出异步 `createApplication(options)` 与内部 `buildApp(context)`。import 不读 dotenv、不打开默认双库、不建目录、不启动定时任务；路由与依赖按实例创建，不操作 require cache 或全局 process.env。
- 连接/路径工厂分别等待双库打开、PRAGMA、兼容初始化和站长 bootstrap。任一步失败关闭连接并拒绝，server 不监听。默认生产路径、相对 DB_PATH/LOG_DB_PATH 的 data 基准保持兼容。
- 旧 SQL 提取到 `legacy-schema.json`，包括 Event 表、双 UNIQUE、FK CASCADE、旧补列和索引。这是兼容初始化器，**不是版本迁移账本**；BM-18 前仍显式执行 CREATE/ALTER。没有运行于原库。
- storage、backup、Bot、Umami 缓存和限流 store 都在实例 context 内。测试显式提供 env、data/public/backups，监听 loopback 随机端口；NODE_ENV=test 缺路径即拒绝。Bot 与备份执行可以关闭，即使误配 Webhook URL 也不发送；测试没有 Umami 凭据。
- 三个定时任务在 listen 成功后开启。close 停接请求、清除定时器、等待跟踪任务、shutdown 限流 store、关闭双库；重复 close、监听失败和 close/listen 竞态均有测试。
- server 保留 dotenv 和原启动命令，等待 ready 后监听；错误退出非0，SIGINT/SIGTERM 有基础关闭。未改生产 Dockerfile、依赖版本、npm lock、shared/workspace、Nuxt 或部署。
- 审计写使用带错误回调的单条 run，避免 Statement 未处理 error；仍是尽力写入，没有跨库事务或可靠投递承诺。

## 失败与环境修复

1. 初始测试直接 import 旧 app，触发了旧 dotenv 读取；随后因 sqlite3 缺原生 binding 失败，未到目录创建/数据库连接，没有输出密钥值。这次入口选择不符合规划的隔离要求，之后移除 app 的 dotenv 并只用显式 fixture。默认 TEMP 的 mkdtemp 又返回 EPERM，改为工作区专用 TEMP/TMP。
2. Windows 原路径两次 npm ci 因缓存/node-gyp/build 权限失败。相同 package/lock 复制至 `.tools/backend-install`，显式 Node24、工作区 npm cache/TEMP 下 `npm ci --no-audit --no-fund` 成功（249 packages）。随后 backend 执行 `npm ci --ignore-scripts --no-audit --no-fund`，复制本次干净安装的 sqlite3 `build/Release/node_sqlite3.node` 回本地 node_modules。Windows 最终使用 backend 自己的依赖；没有提交二进制。**原路径带 scripts 的 Windows npm ci 尚未成功**，不能当作 BM-03/04 的 Windows 干净安装验收。
3. 初始清理 hook 在连接关闭前删除临时根，造成失败并遗留运行；已改为先关闭 fixture 全部实例、核验绝对临时路径前缀再删除。失败进程已结束，新测试自然退出。
4. 尝试由 Node 子进程调 Docker，因 buildx lock、Docker named pipe 权限失败，临时包装器已删除。最终由 PowerShell 直接调 Docker 完成 Linux 验证。
5. diff 检查发现新写 CRLF 被识别为尾随空白；统一本批文本 LF 后通过。
