## 1. 目标与决策

目标是降低公开页面延迟波动，保证登录撤销、访客投稿、资源发布与备份在并发和重启下行为正确，并为后续多实例部署准备数据库边界。

当前默认路线：**先完成低风险优化并建立基线，再决定是否迁移 PostgreSQL。** PostgreSQL 迁移作为独立、有完整验收和回退方案的项目准备，不与界面更新、会话重构、部署切换同时发布。

若近期已确定多实例部署，可在基线建立后直接启动 PostgreSQL 适配；仍须完成减少无效写入和草稿原子更新，但不再投入完整的 SQLite Worker 方案。

本轮仅规划。后续实施保留工作区改动供用户 review，不自动提交、推送或切换生产。生产性能、配置和数据规模均以实施前重新检查为准。

## 2. 已确认的依据

- BFF 使用同步 SQLite，在成功鉴权时写入 lastSeenAt，并在 set 时遍历会话；访客草稿更新为 delete 后 set，存在独立提交间隙。
- 后端数据库适配器每次操作建立、关闭连接；静态图片请求经过封禁查询。
- 资产发布存在写事务内扫描全站资源引用的路径，扫描范围包含历史版本。
- 活动正文只缓存原始记录，没有缓存 Markdown 渲染结果；日志页和成员页首屏存在独立请求串行等待。
- events 缺少匹配列表查询的索引。是否构成生产瓶颈仍须通过查询计划、耗时与负载验证。
- 检查时生产 Umami 数据目录是 /opt/umami/umami-db-data，已经位于工作树外；仓库默认配置仍需加固。
- 检查时应用自动备份关闭，新的宿主机备份任务未启用。站外目标指定为阿里云 sshali；加密公钥、专用传输凭证、通知渠道与真实恢复验收尚待完成。
- 后端公开日志已有脱敏；活动详情的历史请求关闭了首次请求。这两项不作为缺陷修复。

## 4. S0：建立基线

### 工作

1. 记录 Git revision、镜像 revision、Node/数据库版本、实际挂载、容器资源上限、备份调度 owner。
2. 统计业务表行数、内容与历史版本体积、会话数、审计增长量；只输出聚合信息，不输出凭证、IP 或正文。
3. 在隔离环境使用脱敏副本或合成数据，分别测冷缓存、热缓存、后台轮询、并发写入和图片处理。
4. 记录公开页 TTFB P50/P95/P99、事件循环延迟、鉴权耗时、写盘次数、连接创建次数、写锁等待、database_busy、RSS、CPU、WAL 与队列长度。
5. 准备当前版本完整备份，并在独立目录恢复，确认数据库和引用资源能被应用读取。

### 验收

固定机器资源、数据集、并发与请求组合，可重复运行。同组实验至少重复三次，记录分布，不仅比较平均数。

代表性负载取实测业务高峰，并增加 3 倍压力场景；会话、内容和历史版本增加一档数据规模用于观察增长趋势。最终阈值在本阶段固定，不能测试结束后为了通过而修改。

## 5. S1：会话存储与授权正确性

### 先做低风险改动

- 区分关键状态与活动时间。创建、撤销、身份变更、草稿授权和提交回执可靠提交后才返回成功。
- 成功鉴权且身份未改变时，不重写整个会话。lastSeenAt 如确有用途，最多每 60 秒合并落盘；固定 expiresAt 的语义保持不变。
- 缓存预编译语句；将全量 sweep 从每次 set 移除，改成有上限的批处理，删除在事务内合并。
- 将草稿 delete/set 改成一次原子持久化更新；内存中的顺序维护不能额外删除持久化记录。
- 明确写失败时内存与数据库的状态，不允许“返回成功但没有持久化”，也不允许失败的撤销重新开放会话。
- 确认重复提交的业务幂等边界：后端提交成功、BFF 回执未落盘时应可查询确认；不能把内存中的进行中标记当成跨重启的幂等保证。

### Worker 的决策条件

完成以上改动后，如果仍能证明持久化导致公开页事件循环延迟，再考虑 SQLite Worker。Worker 需要异步存储接口、有界队列、操作顺序、超时后结果确认、故障恢复及停机排空。

若已选择 PostgreSQL，直接实现异步 PostgreSQL 存储，避免建设随后废弃的 SQLite Worker。WAL/NORMAL 不作为绕过持久性要求的默认修复；关键撤销仍须满足既定恢复保证。

### 必测场景

- 登录、注销、用户撤销与在途鉴权竞争；已撤销会话不可复活。
- 草稿更新时强杀、写盘失败、提交成功但响应丢失、重复提交。
- 重启后恢复状态与过期规则正确，损坏记录不能误授权。
- 同时运行管理端轮询与公开页访问，验证同步写次数和延迟变化。

## 6. S2：数据库与页面性能

### 数据访问

- 用有界连接复用替代每 SQL 开关连接。事务必须独占连接，并保留当前事务作用域、取消、关闭和错误映射保证。
- 禁止多个请求交错复用同一写事务；连接借出和归还均有明确失败处理。
- 封禁查询使用有容量限制的短期缓存，封禁和解封提交后主动失效。数据库故障时区分“无封禁”和“查询失败”，明确是否使用最近有效状态。
- 静态资源是否绕过封禁检查作为显式行为决策，不能靠移动中间件悄悄改变策略。
- 用 EXPLAIN QUERY PLAN 验证 events、members 的真实查询，再通过新增迁移补索引；不要修改已发布迁移文件。
- 记录 WAL/checkpoint 进度和长事务，不用连接数量推断 WAL 泄漏。

### 资源引用与页面

- 为资产引用建立规范化关系及重建工具，避免发布事务中扫描所有富文本和历史版本。
- 引用关系与业务记录同事务更新。上线前对比新旧扫描结果，保留软删除和历史版本引用；存在差异时拒绝物理清理。
- Markdown 渲染缓存按内容摘要及渲染/安全规则版本区分，限制条目数和总字节，并合并相同内容的并发渲染。发布、回滚及安全规则升级不得使用旧结果。
- 日志页、成员页独立请求并行发起，保留 SSR hydration、错误提示和筛选缓存隔离。
- 资源列表测量大目录下的 DOM 数和交互延迟，再采用窗口化或分页；不对无限累积条目执行进入动画。

### 验收

目标负载下无新增权限或事务回归；明确记录优化前后的连接数、写锁等待、渲染次数和 P95/P99。候选版本出现超过基线 10% 的持续延迟退化时停止发布并定位，不能仅以平均响应改善判定通过。

## 7. S3：运维和容量闭环

- 备份绑定本次唯一 tag，验证明确产物；不得用全目录最大 mtime 推断本轮成功。
- 自动检测备份调度 owner，确保应用与宿主任务只有一个启用入口。
- 配置腾讯云到阿里云的专用传输凭证和核验过的加密公钥；解密私钥由独立受控位置保管。
- 完成真实上传、下载、解密、网站恢复及 Umami 空库导入。恢复凭证必须关联源备份标识，不能只靠远端文件 mtime 判断成功。
- 保留策略默认超过 30 天且不在最新 7 份内才可删除，并保护最后有效恢复点；先预览再验证实际清理。
- 配置通知渠道，验证探测故障、恢复、备份超龄、磁盘阈值和恢复失败通知。空 webhook 不算验收完成。
- 生产数据默认路径移出工作树；数据库挂载缺失应失败，防止静默初始化空库。补齐 .dockerignore 中数据及不必要内容。
- 对 Umami/Postgres/Komari 制定资源预算，结合业务峰值调整现有 web/backend 上限；不得机械照抄权限和资源配置。
- 头像上传使用报名流程凭据、单文件/每来源容量预算和未引用回收；不要求公开报名头像拥有投稿草稿证明。
- 在 CI 中检查构建镜像的 Healthcheck 配置及真实探针，补齐现有功能测试未覆盖的运行契约。

## 8. D1：是否进入 PostgreSQL 迁移

满足以下任一条件时评估启动：

1. 已明确需要多个应用实例共享数据和会话。
2. 完成连接、索引和事务优化后，代表性负载仍持续出现不可接受的写锁等待或 database_busy。
3. 已确定需要数据库独立部署，或需要建设持续归档/时间点恢复并能承担对应运维。

不以“PostgreSQL 更专业”或“已经有 Umami 的 PostgreSQL”作为迁移依据。

继续 SQLite：记录性能容量边界、复查条件，完成必要的 worker/资源预算即可。
选择 PostgreSQL：记录选择原因、目标版本、实例资源预算、迁移范围和恢复目标；进入以下阶段。

## 9. P1：PostgreSQL 适配和导入

### 目标结构

- 网站使用独立数据库和最小权限账号；Umami 保持独立数据库及账号。
- 是否共用 PostgreSQL 实例由资源和故障影响评估决定；共用实例不等于故障隔离。
- 业务、审计与 BFF 状态分表/模式及权限；跨实例能力凭据的读取、撤销必须由权威存储保证，不能继续完全信任每实例内存副本。
- 初次迁移保持现有审计 outbox 和文件发布协议，不顺便重写事件、上传或权限系统。
- 文件仍由现有文件存储管理。迁移数据库本身不等于已经支持多实例；发布目录、任务租约、限流和缓存失效另需验收。

### 代码和数据工作

- 建立异步数据库接口、连接池及事务专用连接；参数绑定、事务超时、取消和错误码映射有契约测试。
- 清点 INSERT OR REPLACE/IGNORE、strftime、PRAGMA、自增 ID、lastID、JSON 文本、布尔值、空字符串、NULL 和时间语义，逐项适配。
- 排查当前依赖串行写入的先查后改逻辑；通过约束、条件更新或必要的行锁保证并发正确性，设计有限死锁/序列化失败重试。
- 编写只读 SQLite 导出和 PostgreSQL 导入工具，保留 ID、外键及历史关系，导入后校准序列。
- 不符合目标类型或约束的数据输出脱敏诊断并停止导入，禁止静默丢弃、截断或修改业务含义。
- 校验表行数、主键集合、外键、关键字段规范化摘要、时间往返、软删除、历史版本、审计 outbox、资产引用与权限状态。
- BFF 切换优先选择受控重新登录，减少迁移能力凭证的风险；访客未完成草稿须安排排空窗口或明确迁移方案，不静默失效。

## 10. P2：生产副本演练

在隔离网络和私有目录中使用授权副本；禁用真实通知、机器人外发和所有生产定时任务。

必须验证：登录/撤销、投稿与重复请求、报名、内容发布/恢复、软删除、图片引用、审计、备份和恢复；同时进行并发竞争及故障注入。

完整演练至少包括：从 SQLite 导入 → 应用只读检查 → 隔离写入测试 → PostgreSQL 备份 → 空实例恢复 → 行为和引用校验。

记录实际切换耗时、所需磁盘空间和恢复耗时，以此确定维护窗口。PITR 若被列入迁移收益，必须配置 WAL 归档并演练恢复到指定时间；仅有 pg_dump 不算 PITR 完成。

## 11. P3：生产停写切换与回滚

### 切换步骤

1. 公布维护窗口，暂停所有写入口、机器人消费、定时任务和备份调度，等待在途写入排空。
2. 生成最终数据库与文件恢复点，记录 revision、校验值及配置版本。
3. 导入空的目标数据库，执行完整数据校验和只读业务冒烟检查。
4. 切换候选应用连接配置；后台任务仍暂停，验证探针和关键读取。
5. 所有放写前条件通过后开放写入，逐项恢复任务；记录“第一笔 PostgreSQL 生产写入”的边界。
6. 在一个完整业务周期内观察错误率、延迟、连接池等待、锁等待、任务积压与磁盘增长，并完成至少一次真实备份恢复验证。

### 回滚规则

- PostgreSQL 尚未接收生产写入：停止候选应用，切回旧镜像与冻结的 SQLite 恢复点。
- 已接收生产写入：禁止直接切回旧 SQLite。先停写，保存 PostgreSQL 和文件现状，再采用已演练的反向数据迁移，或在 PostgreSQL 上修复/回退兼容应用版本。
- 未准备反向迁移时，放写后只能按“前向修复或 PostgreSQL 恢复”处理，必须在切换前接受此边界。
- 观察期保留旧数据及旧镜像，不自动删除。只有用户验收后才计划退役。

## 12. 验证与交付

按实际改动选择测试，并运行仓库要求的检查。已有入口包括：

- 根目录 pnpm typecheck、pnpm lint、pnpm test、pnpm build。
- backend 的 test:integration、test:contracts、test:bff；涉及界面行为时运行对应 E2E。
- 备份恢复、锁竞争、持久化崩溃、授权竞争与保留保护专项测试。
- 生产镜像运行验证，不只验证源码测试；Node 版本遵守仓库 24.16.0 至 25 之前的要求。

每阶段交付：改动范围、风险说明、测试与性能对比、恢复/回滚步骤、未完成项。测试数量、脚本存在、文档写完均不替代真实部署验收。

## 13. 推荐执行顺序

先 S0 → S1；S2 按连接复用、索引、渲染缓存、资产引用优化拆开实施；S3 独立完成真实运维闭环。取得测量结果后执行 D1。

本计划不预设迁移一定发生，也不先承诺多实例或高可用。若选择迁移，则必须走完 P1 → P2 → P3，避免只换驱动后直接上线。
